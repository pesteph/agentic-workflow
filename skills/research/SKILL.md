# Research

You investigate an open question and produce a **cited research report**. Research is read-only: you gather and synthesize evidence, you do not change code.

> **Harness note:** Some harnesses (e.g. GitHub Copilot CLI) provide `/research` as a built-in agent — there this Skill is not installed. On harnesses without a built-in (e.g. Claude Code), this Skill provides the capability.

## Execution

**Delegate** the investigation to a Sub-Agent with a **read-only toolset** (search, fetch, read — no edit, no build). The Sub-Agent has a fresh context window and runs the investigate→synthesize loop. Show the user the complete report.

**Timeout:** Research is either fast or stuck. If the Sub-Agent shows no progress after 5 minutes, abort and do it yourself (Rule 26 / Rule 8).

## Input

A **research prompt** — ideally the copy-paste-ready prompt generated by `/analyze` (persisted in the session, e.g. `files/research-prompt.md`). If no prompt is given, ask the user what exactly should be researched, then write the prompt yourself before starting.

## Sources — investigate three in parallel

1. **Codebase** — search the local project for existing implementations, patterns, libraries, and formats BEFORE declaring anything "new ground". Tools: Grep, Glob, Read.
2. **Web** — official documentation, framework guides, community patterns, real-world production experience. Tools: the harness's web search and fetch capability (e.g. WebSearch + WebFetch).
3. **Public repositories** — real usage examples and issue discussions. Tool: `gh search code|repos|issues` via the shell, plus fetching specific files.

Read technical facts from project files (versions, dependencies) per Rule 20 — never assume them.

## Research discipline (hard rules)

- **No assumptions.** Every statement about runtime behavior, data formats, or API behavior is backed by evidence (code path, doc link, real sample) or flagged as an open question. "I think" / "probably" is not a result.
- **Validate against real data.** Claims about business data ("amounts can be negative", "quantity is always 1") MUST be checked against real sample files, programmatically — not speculated. Binary files (XLSX, PDF, …) must be read programmatically; "I can't read it" is not acceptable.
- **Cross-check generated docs.** Pre-existing research docs (e.g. produced by a cloud agent) are NOT a trusted source — they may mirror wrong code instead of real data. Always verify against the original source.
- **Look up framework behavior, don't claim it.** Before citing a framework pattern as an argument, open the base class / interface / implementation and verify the behavior in code.
- **Cite everything.** Every finding carries its source: file:line, doc URL, repo+path, or sample file. Uncited findings are not findings.

## Confidence

Never ask the user clarifying questions mid-research — make a reasonable assumption, proceed, and record it in a **Confidence Assessment** section so the user can correct it.

## Output Format

Write the report to a known path (e.g. `files/research-report-<topic>.md`) so later Skills can consume it 1:1 (`/brief` copies technical details verbatim — Rule 10).

```
## Research: [Topic]

### Question
[The precise question being researched]

### Summary
[3-5 sentences: the answer, the key findings]

### Findings
| # | Finding | Evidence (source) | Confidence |
|---|---------|-------------------|------------|
| 1 | [Concrete fact] | [file:line / URL / repo:path / sample] | High/Medium/Low |

### Technical Details (verbatim — for /brief)
[Config keys, field names, casing, formats, example values — stated exactly, not abstracted. Information loss here causes semantic bugs downstream.]

### Confidence Assessment
[Assumptions made, what could not be verified, what the user should confirm]

### Open Questions
[What remains genuinely unanswerable by research → for /discuss or the user]

## Workflow State (update in plan.md)
- Completed Skill: /research
- Result: [1-2 sentences: the answer + confidence]
- Next Skill: [/conceptualize | /design (re-entry after a research loop) | /discuss]
- Context for next Skill: [Path to the research report]
```

💡 Context maintenance: Research reports are token-intensive. Update plan.md first, then consider context compaction.
